## 설계 결정

- **장애 주입과 반응형 명령 루프는 동시에 쓸 수 없다**: 반응형 루프(`_run_reactive`,
  `simulator/main.py`)는 매 틱 실시간으로 자세를 계산하며 명령을 끼워 넣는 방식이라,
  "미리 계산해둔 전체 시퀀스를 변형"하는 장애 주입(`--faults`/`--loss-rate`/
  `--reorder-window`)과 구조적으로 양립할 수 없다. `real_time and not fault_types and
  loss_rate == 0.0 and reorder_window <= 1`일 때만 반응형 루프를 쓰고, 그 외에는 기존
  사전계산 경로를 그대로 둔다(둘 다 유지).
- **Grafana 데이터소스 uid를 수동으로 고정**: 명시하지 않으면 Grafana가 재프로비저닝마다
  새 uid를 자동 생성해 대시보드 JSON이 매번 깨진다 — `datasources/prometheus.yml`에
  `uid: prometheus`를 직접 박아뒀다.

### 부하 시험 (10대 × 1Hz, 22분)

실제 `docker compose` 스택(postgres+redis+api+prometheus+grafana) 대상, 장애 주입 없이
22분(1320초) 연속 실행:

- 시뮬레이터: 13200건 전송(10 × 1320 정확히 일치), 에러 로그 0건, 정상 종료.
- `aeroops_telemetry_processing_latency_seconds` p95: 시험 내내 **238~241ms로 안정**
  (SLO 500ms 이하 대비 절반 이하, 시간에 따른 증가 추세 없음 — 메모리/커넥션풀 누수로
  인한 점진적 열화 징후 없음).
- `aeroops_telemetry_rejected_total`: 0건(계약 위반 없음).
- **병목 없음**: 22분 동안 처리 지연이 전혀 흔들리지 않아, 현재 규모(10대×1Hz)에서는
  수집 경로에 유의미한 병목이 없다고 판단.
- 참고: 같은 DB를 시드 고정(`seed=42`)으로 여러 번 재실행하면 `telemetry_duplicate_total`이
  거의 전체 건수만큼 올라간다 — 매 실행이 `sequence_no=0`부터 다시 시작해 이전 실행이
  이미 기록한 더 큰 sequence_no보다 뒤처진 것으로 판정되기 때문(중복 판정 로직은
  의도대로 동작한 것). 다음에 같은 시험을 반복할 땐 DB를 초기화하거나 seed를 바꿔야
  이 숫자에 혼동이 없다.

### 장애 시험 (Redis/Postgres 중단 → 복구) — 버그 발견 및 수정

최초 시도(22분 부하 중 Redis 30초·Postgres 30초 순차 중단)에서 **Redis 재시작 이후
텔레메트리 수신이 영구히 멈추는 버그를 발견**:

- 원인: `backend/app/core/redis_acl.py`가 앱 시작 시 1회만 `telemetry`/`command` 전용
  Redis ACL 사용자를 등록한다(`app/main.py` lifespan). 이 프로젝트의 dev
  `docker-compose`는 Redis에 영속 볼륨을 붙이지 않아, `docker stop`/`start`만으로도
  Redis가 완전히 빈 상태로 돌아오고 그 ACL 사용자들이 함께 사라진다. 이후 모든 요청이
  `redis.exceptions.AuthenticationError`로 영구히 실패했다(앱 재시작 전까지).
  텔레메트리 소비 루프(`telemetry/consumer.py`의 `run_consumer_loop`)도 `xreadgroup`/
  `xack` 호출을 감싸는 예외 처리가 전혀 없어, 이 에러 한 번으로 백그라운드 task 자체가
  영구히 죽는 2차 문제도 함께 발견.
- 수정:
  - `app/core/redis_acl.py`에 `xadd_with_acl_retry()` 추가 — `AuthenticationError`
    (`ConnectionError`의 하위 클래스) 발생 시 ACL 재등록 후 1회 재시도. `ingestion/router.py`,
    `command/router.py`의 명령 발행 경로에 적용.
  - `telemetry/consumer.py`의 `run_consumer_loop` 전체를 try/except로 감싸, Redis
    레벨 예외 시 ACL·consumer group을 재등록하고 루프를 계속 돈다(`RECONNECT_BACKOFF_S`
    대기 후 재시도).
  - 회귀 테스트: `backend/tests/test_redis_acl.py`에
    `test_xadd_with_acl_retry_recovers_after_acl_user_disappears` 추가 — `ACL DELUSER`
    + 커넥션 풀 강제 재연결로 "Redis 재시작으로 사용자가 사라진 상태"를 재현하고, 재시도
    없는 맨 `xadd`는 여전히 실패하지만 `xadd_with_acl_retry`는 복구됨을 확인.
- 수정 후 재검증(6분, Redis 30초+Postgres 30초 순차 중단): 텔레메트리 수신률이 각
  장애 구간에서 일시적으로 떨어졌다가(Redis 중단 시 0까지, Postgres 중단 시 일부만)
  수십 초 내 자동으로 정상 수준(~9.2/s, 10대 기준)으로 복귀. `aeroops_telemetry_consumer_error_total`도
  장애 구간에서만 12건 증가하고 이후 더 늘지 않음(과거엔 무한정 증가).

## 남은 이슈 / 다음 단계로 이월

- 이번 장애 시험은 Redis·Postgres를 수동으로 `docker stop`/`start`해 재현했다.
  WebSocket 중단·재연결은 Node 스크립트로 별도 확인(연결 종료 후 재연결 시 서버가
  최신 스냅샷을 다시 보냄, `realtime_ws_connections` 게이지 정상 복귀) — 끝.
- 손실(`--loss-rate`)·지연(`--faults delay`)·역순(`--reorder-window`)·명령 timeout
  재현 시나리오는 시뮬레이터 옵션으로 이미 지원되고 2단계 보정에서 유닛 테스트로
  검증됐지만, 이번 7단계 마무리에서 **실제 docker compose 스택 대상으로 다시 돌려
  확인하지는 않았다** — 필요하면 8단계 "전체 회귀시험(손실·지연·역순·단절·재동기화)"에서
  함께 묶어 확인한다.
- Redis ACL 재등록 재시도는 "한 번만" 재시도한다 — Redis가 수십 초 이상 계속
  불안정한 상황(반복적인 flapping)은 다루지 않는다. 프로덕션에서는 영속 볼륨/복제를
  갖춘 관리형 Redis를 쓸 가능성이 높아 ACL 소실 자체가 거의 발생하지 않겠지만, 연결
  단절 자체에 대한 일반적 재시도/백오프는 8단계에서 더 다룰 수 있다.
- 브라우저로 실제 화면을 열어 재생 화면 3종 동기화를 눈으로 확인하지는 못했다(세션에
  브라우저 제어 도구가 연결되지 않음) — lint/build/vitest + 백엔드 통합 테스트로만
  검증했다.
