## 설계 결정

- **계약 중복 구현**: backend/simulator가 각자 Docker 빌드 컨텍스트를 가지므로(모노레포지만
  컨테이너 경계 분리) 공유 패키지 대신 계약을 양쪽에 독립 구현하고 데이터 사전을 SSOT로 삼는다
  ([ADR 0002](../../decisions/0002-telemetry-contract-duplication.md)).
- **heading vs yaw**: `heading_deg`(지면 진행 방향, [0,360))와 `yaw_deg`(기수 방향, [-180,180])를
  별개 필드로 유지. 무풍 시나리오에서는 두 값이 같지만 계약·화면 모두 구분해서 다룬다.
  기본 시나리오는 무풍을 가정하므로 실제로는 `yaw_deg = to_signed_deg(heading_deg)`.
  같은 이유로 `roll_deg`/`yaw_deg`/`pitch_deg`는 서로 다른 범위([-180,180] / [-180,180] / [-90,90])를
  갖는다.
- **장애 주입은 "전송 순서/누락/값 이상"만 표현, 계약 위반은 만들지 않음**: 계약 위반(범위
  이탈) 검증은 별도 테스트(`test_telemetry_schema.py`, `test_contracts.py`)로 다룬다.
- **전송 계층 분리(Sink)**: 로드맵 완료 기준이 "정상 프레임은 계약 검증을 통과한다"이지 "실제
  HTTP 전송이 성공한다"가 아니므로, 3단계에 생길 `/telemetry` 엔드포인트 없이도 시뮬레이터를
  독립적으로 끝까지 검증할 수 있게 sink를 추상화했다.
- **시뮬레이터 CLI를 `run` 서브커맨드로 유지**: Typer는 명령이 하나뿐이면 서브커맨드 이름 없이
  바로 호출되게 축약하는데, 기존 `simulator/Dockerfile`의
  `CMD ["python", "-m", "simulator.main", "run"]`과 README 예시가 `run`을 서브커맨드로
  기대하고 있어 `@app.callback()`을 추가해 그룹 모드를 강제했다.

### 구현 내역

- **`TelemetryFrame` 추적성 필드**: `backend/app/schemas/telemetry.py`,
  `simulator/simulator/contracts/telemetry.py`에 `operation_session_id`, `deployment_id`,
  `correlation_id`(모두 optional) 추가. `docs/api/telemetry_frame_dictionary.md` 갱신.
- **`CommandEnvelope` 계약 신설**: `backend/app/schemas/command.py`,
  `simulator/simulator/contracts/command.py` — `docs/planning/05_데이터엔지니어링_아키텍처.md`가
  명시한 11개 필드 그대로 구현, `expires_at > issued_at` model validator 포함.
  [`docs/api/command_envelope_dictionary.md`](../../api/command_envelope_dictionary.md) 신설.
- **채널 분리 테스트**: `backend/tests/test_command_schema.py`,
  `simulator/tests/test_command_contract.py`의 `TestChannelSeparation` — Telemetry 모양
  데이터로 `CommandEnvelope` 검증 시 실패, 그 반대도 실패함을 확인(필드 집합이 겹치지 않아
  별도 로직 없이 계약 자체가 분리를 강제).
- **기체 측 Command 처리 시뮬레이션**:
  [`simulator/simulator/command_handler.py`](../../../simulator/simulator/command_handler.py)의
  `DeviceCommandHandler` — `acknowledge()`(ACK), `process()`(만료 확인 → 확률적 성공/실패,
  `last_processed_command_id` 갱신). 아직 실제 Command 채널이 없어 CLI에는 연결하지 않고
  단위 테스트로만 검증(3단계 보정 이후 실제 dispatch 경로에 연결한다).
- **장애 주입기 확장**: `simulator/simulator/faults.py`에
  - `apply_packet_loss(frames, rng, loss_rate)` — 프레임별 독립 확률로 손실(연속 방식).
  - `apply_reorder_window(frames, rng, window_size)` — 겹치지 않는 구간 단위로 순서 셔플.
  - `inject_delay`에 `max_shift` 추가(지연 분포 상한).
  - `apply_faults`가 `fault_kwargs`(유형별 파라미터 오버라이드)를 받도록 확장.
  - `compute_sequence_gaps(frames)` — 재현성 검증용 헬퍼.
  `simulator/simulator/main.py`에 `--loss-rate`, `--reorder-window`, `--delay-min-shift`/
  `--delay-max-shift`, `--disconnect-min-duration`/`--disconnect-max-duration`,
  `--gps-jump-min-m`, `--battery-drop-pct` CLI 옵션 추가.

### 설계 결정

- **이산 방식과 연속 방식을 공존**시켰다: 기존 `inject_*`/`--faults`(정확히 1건/1구간만 주입,
  결정론적이고 "6개 이상 장애 시나리오 테스트"에 적합)를 그대로 두고, `apply_packet_loss`/
  `apply_reorder_window`(확률·윈도우 기반, 실제 네트워크 손상에 더 가까움)를 **별도 레이어**로
  추가했다. 기존 테스트·문서(완료된 2단계 dev_history)를 깨지 않으면서 새 요구사항을
  만족시키기 위함이다.
- **`CommandEnvelope`은 상태를 갖지 않는다**: 상태 머신(`DRAFT→...→CANCELLED`)은 계약이 아니라
  `command_events` 테이블(3단계 보정)과 `command` 모듈(5단계)의 책임으로 분리했다 — 계약은
  "명령 하나의 불변 스펙"만 표현해야 이후 재생(7단계)에서 같은 명령을 안전하게 재구성할 수
  있다.
- **`DeviceCommandHandler.process()`는 만료 여부와 무관하게 `last_processed_command_id`를
  갱신**한다 — 재동기화 시 서버가 "이 기체가 이 명령까지는 처리(시도)했다"를 알아야 하며,
  타임아웃도 "처리 결과"의 하나이기 때문이다.

### 남은 이슈 / 다음 단계로 이월

- `DeviceCommandHandler`는 아직 실제 Command 채널(Redis stream, `/commands` API)에 연결되어
  있지 않다 — 3단계 보정에서 최소 골격이 생기면 연결한다.
- `command_type`은 자유 문자열이다(`RTL`, `SET_MISSION` 등 구체적 값 집합을 강제하지 않음) —
  실제 값 집합은 5단계 `command` 모듈이 검증할 때 확정한다.
- `TelemetryFrame`의 새 추적성 필드(`operation_session_id`/`deployment_id`/`correlation_id`)는
  아직 DB에 저장되지 않는다(컬럼 없음) — 저장은 "3단계 보정"/7단계에서 migration과 함께
  추가한다.
