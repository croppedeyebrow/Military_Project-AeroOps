### Alert

- [`app/modules/alert/rules.py`](../../../legacy-backend/app/modules/alert/rules.py): 순수 함수
  3종(배터리 경고 20%/위험 10%, RSSI 경고 -100dBm, 지오펜스 — ray-casting 알고리즘으로
  PROHIBITED 폴리곤 내부 판정). `RULE_VERSION` 상수로 버전 추적.
- `repository.py`: `evaluate_and_raise_alerts` — 같은 `asset_id`+`alert_type`의 `OPEN`
  경보가 이미 있으면 새로 만들지 않는다(배터리가 낮은 상태가 수백 프레임 지속돼도 경보
  하나만 유지). `acknowledge_alert`/`resolve_alert` 상태 전이.
- `telemetry/consumer.py`에 연결: 최신 상태가 실제로 갱신될 때만(중복·역순 제외) 규칙을
  평가하고, 새 경보를 `/ws/operations`에 `{"type": "alert", ...}`로도 즉시 브로드캐스트.

  진행 보고), `force_timeout`.

## 설계 결정

- **명령 생성 시점이 아니라 승인 시점에 Redis 발행**: 3단계 보정에서는 `POST
  /commands`가 곧바로 Command Stream에 발행했다. 상태 머신이 없던 그때는 "발행 =
  생성"이 자연스러웠지만, 지금은 "승인되지 않은 명령이 기체가 볼 수 있는 채널에
  나타나면 안 된다"가 완료 기준이라 발행 지점을 승인(그리고 자동 dispatch) 성공 시로
  옮겼다.
- **`DRAFT` 상태는 만들되 실제로 쓰지 않는다**: `POST /commands`는 완전한 요청(대상·
  파라미터·만료 시각 포함)이라 이미 "승인을 구하는" 상태다. `DRAFT`는 상태 머신 문서와
  호환성을 유지하면서, 나중에 "제출 전 임시 저장" 기능이 필요해지면 쓸 자리로 남겨뒀다.
- **승인은 곧 자동 전달**: 사람이 "승인"과 "전달"을 별도로 누르게 하지 않는다 —
  승인 즉시 만료 여부만 다시 확인하고 바로 `DISPATCHED`로 넘어간다. 실제 기체 dispatch
  worker가 따로 없는 MVP 단계에서 별도 "전달" 사람 행동을 추가하는 건 과한 마찰이라고
  판단했다.
- **"ACK 손실 시 무조건 재실행 안 함"은 설계로 자동 충족**: 시스템 어디에도 "ACK 없으면
  자동 재시도"하는 코드 경로가 없다(타임아웃 워커는 재시도가 아니라 `TIMED_OUT`
  종결일 뿐). 그래서 이 완료 기준은 별도 로직 없이 항상 참이다 — 테스트로 이 부재를
  명시적으로 확인해뒀다.
- **감사 로그는 공통 데코레이터가 아니라 명시적 호출**: 호출 지점이 8곳 정도뿐이라
  데코레이터/미들웨어로 감추면 오히려 "어디서 감사 로그가 남는지" 추적하기 어려워진다
  판단했다.
- **지오펜스 판정은 순수 Python ray-casting**: PostGIS `ST_Contains` 공간 질의도 가능
  하지만, 지오펜스 수가 적은 MVP 규모에서는 프레임마다 왕복 질의를 늘리는 것보다
  이미 메모리에 있는 폴리곤 좌표로 순수 함수 계산이 더 간단하고 테스트하기 쉽다.

## 테스트/검증

```
cd backend && ruff check .   # 통과
cd backend && pytest         # 서비스 없음: 30 passed, 78 skipped(신규 통합 테스트 포함)
                              # 서비스 있음(docker postgres+redis): 108 passed, 3회 반복 확인(타이밍 이슈 없음)
cd simulator && pytest && ruff check .   # 50 passed, 변경 없음(회귀 확인)
cd frontend && npm run lint  # 0 errors, 기존 2개 경고만(의도된 패턴)
cd frontend && npm run build # 통과
cd frontend && npm run test  # 28 passed(신규 layers.test.ts 3건 포함)
```

실제 Postgres/Redis(임시 docker, 검증 후 삭제) + 실제 backend 서버 + 실제 시뮬레이터로
end-to-end 확인:

- 임무 생성 → `ACTIVE`로 상태 변경 → 예정 경로 설정 → `GET /missions/{id}/route`로
  조회, 지오펜스 생성 → `GET /geofences` 조회 — 전부 프론트 타입과 정확히 같은 모양의
  JSON으로 응답됨을 확인.
- 시뮬레이터로 지오펜스 안쪽을 도는 3대의 텔레메트리를 실제로 흘려보내
  `GEOFENCE_BREACH` 경보 3건이 실제로 생성됨을 `GET /alerts`로 확인.
- `POST /commands` → `/approve`(자동 dispatch) → `GET /commands/{id}`로 이벤트 이력
  (`CREATED → APPROVED → DISPATCHED`)이 정확한 순서로 남는 것을 실제 HTTP 호출로 확인.
- Node 내장 WebSocket으로 `/ws/operations`에 접속해 낮은 배터리 텔레메트리를 보내면
  `update` 메시지 다음에 `alert` 메시지가 실제로 도착하는 것을 확인(프론트 타입과
  필드까지 일치).

완료 기준 대비: 위 "완료 기준" 절 참고 — 전부 충족.

## 남은 이슈 / 다음 단계로 이월

- Command Redis Stream을 실제로 소비해 "기체"에 전달하는 주체가 아직 없다 — 8단계
  mTLS로 실제 기체 연결이 붙기 전까지는 `/commands/{id}/ack|execute|result`를 사람이나
  시험 스크립트가 직접 호출해 기체 역할을 대신해야 한다.
- 지오펜스 판정은 매 프레임 전체 지오펜스를 다시 읽는다(구역 수가 적어 문제없음,
  늘어나면 캐싱 고려).
- 감사 로그는 주 작업과 완전한 outbox 트랜잭션으로 묶이지 않았다(두 커밋 사이 크래시
  시 감사 기록만 유실 가능 — 극히 드묾, 3단계의 알려진 제한과 같은 종류).
- `device_certificates` 테이블은 이번 단계에서 만들지 않았다(8단계 device_identity
  모듈과 함께 만드는 게 더 자연스럽다고 판단).
- 여전히 브라우저 화면을 직접 본 적은 없다 — HTTP/WS 응답 모양과 로직 단위(vitest)는
  검증했지만, 실제 렌더링 확인은 사용자가 `npm run dev`로 열어봐야 한다.
