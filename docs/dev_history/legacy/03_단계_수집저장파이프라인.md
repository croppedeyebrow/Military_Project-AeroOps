### 수집(ingestion) → 스트림 → 소비(consumer) → 저장

- [`backend/app/modules/ingestion/router.py`](../../../legacy-backend/app/modules/ingestion/router.py):
  `POST /telemetry` — 계약 검증 후 `received_at`을 서버 시각으로 채워 Redis Stream
  (`aeroops:telemetry:raw`)에 발행, 202 반환. 저장은 하지 않는다(요청 경로를 짧게 유지).
- [`backend/app/modules/telemetry/consumer.py`](../../../legacy-backend/app/modules/telemetry/consumer.py):
  Redis consumer group으로 스트림을 읽어 `repository.process_frame`을 호출. 앱 `lifespan` 동안
  백그라운드 asyncio task로 상시 실행(별도 워커 프로세스를 추가하지 않음, ADR 0001).
- [`backend/app/modules/telemetry/repository.py`](../../../legacy-backend/app/modules/telemetry/repository.py):
  `INSERT ... ON CONFLICT DO NOTHING`으로 원본 중복을 무시하고, `asset_latest_state`는
  `ON CONFLICT ... DO UPDATE ... WHERE asset_latest_state.event_time < excluded.event_time`으로
  역순 데이터가 최신 상태를 후퇴시키지 못하게 한다(둘 다 애플리케이션 레벨 체크-후-쓰기가 아니라
  DB가 원자적으로 보장).
- [`backend/app/modules/telemetry/router.py`](../../../legacy-backend/app/modules/telemetry/router.py),
  `schemas.py`: `GET /assets/{id}/latest`, `GET /assets/{id}/telemetry`(`start`/`end`/`limit`/`offset`).

## 설계 결정

- **Redis 클라이언트를 이벤트 루프별로 캐싱**(`app/core/redis.py`): 처음에는 프로세스 전역
  `@lru_cache` 싱글턴이었으나, 테스트에서 `TestClient(app)`을 여러 번 여닫을 때마다(각각 새
  이벤트 루프) "Event loop is closed" 오류가 났다. `asyncio.Redis` 커넥션은 자신을 만든 이벤트
  루프에 묶이므로, 실행 중인 루프의 `id()`를 키로 클라이언트를 따로 캐싱하도록 바꿨다. 실제
  서버(uvicorn, 이벤트 루프 하나)에서는 사실상 기존과 동일하게 동작한다.
- **중복 판정 위치**: 원래 계획은 ingestion에서 `asset_id+sequence_no` 조회 후 판정이었지만,
  요청 경로에서 DB를 왕복하지 않도록 판정 자체를 consumer의 `INSERT ... ON CONFLICT`로 옮겼다
  (ingestion은 검증 후 발행만 한다). `docs/planning/02_백엔드_아키텍처.md`의 "오래 걸리는 처리를
  요청 경로에서 실행하지 않는다"와 더 일치한다.
- **테스트 전략**: `backend/tests/test_health.py`, `test_telemetry_schema.py`는 서비스 없이도 항상
  통과해야 하는 단위 테스트로 유지하고, DB/Redis가 실제로 필요한 통합 테스트는
  `test_ingestion_pipeline.py`로 분리해 `conftest.py`의 `require_live_services` fixture로
  자동 스킵되게 했다(`DATABASE_URL`/`REDIS_URL` 연결 실패 시). CI는 항상 서비스가 있으므로 항상
  실행된다.

## 테스트/검증

```
cd backend && ruff check .    # 통과
cd backend && pytest          # 서비스 없음: 16 passed, 7 skipped
                               # 서비스 있음(docker postgres+redis): 23 passed
cd simulator && ruff check . && pytest   # 26 passed (변경 없음, 회귀 확인)
```

로컬에 Docker로 임시 Postgres(PostGIS)·Redis 컨테이너를 띄워 다음을 실제로 검증했다
(수동, `Bash` 세션 — 컨테이너는 검증 후 제거):

- `alembic upgrade head` 성공.
- `POST /telemetry` → consumer 반영까지 end-to-end로 정상 3건 + 중복 1건 + 역순 1건을 보내
  `GET /assets/{id}/latest`가 역행하지 않고, `GET /assets/{id}/telemetry`의 `count`가 4(중복
  제외)임을 확인.
- 잘못된 위경도 프레임이 422로 거부되고 `aeroops_telemetry_rejected_total`이 증가함을
  `/metrics`에서 확인.
- **실제 시뮬레이터 프로세스**를 `uvicorn`으로 띄운 backend에 `--sink http`로 연결해 완전한
  end-to-end(시뮬레이터 → API → Redis → consumer → DB → 조회 API)를 확인.

완료 기준 대비:

- ✅ 10대 데이터를 손실 없이 저장한다.
- ✅ 중복 데이터가 이중 반영되지 않는다.
- ✅ 역순 데이터가 최신 상태를 후퇴시키지 않는다.
- ✅ 기간·기체 조건 이력 조회 테스트가 통과한다.

## 남은 이슈 / 다음 단계로 이월

- **`--no-real-time` + `--sink http` 조합의 한계**: 실제 e2e 검증 중 발견. 시뮬레이터가
  `--no-real-time`이면 `duration-sec` 전체의 미래 `event_time` 프레임을 한꺼번에 만들어 보내는데,
  backend는 `received_at(서버 실제 수신 시각) >= event_time`을 계약으로 강제하므로 각 기체의
  첫 틱만 통과하고 나머지는 consumer가 거부한다(로그+`aeroops_telemetry_consumer_error_total`
  증가, 시스템 다운은 없음). `--real-time`(기본값)에서는 문제없다. `simulator/README.md`에
  캐비어트로 기록함. 근본적으로 고칠지(예: 검증을 완화하거나 시뮬레이터가 real-time만 지원하게
  단순화할지)는 4단계 이후 필요성을 보고 재검토한다.
- consumer 메시지 처리 실패는 재시도 없이 버려진다(dead-letter 없음) — MVP 범위 밖으로 남겨둠,
  `consumer.py` 주석에 명시. **→ 2026-10-24 수정됨**: 일시 실패는 재전달, 영구 실패·재시도 소진은
  dead-letter로 이동([new_history Day 1 보정](../new_history/01_기준선과_전환계약_Day01.md) 참고).
- `GET /assets/{id}/telemetry`는 아직 다운샘플링이 없다(7단계에서 추가 예정, 로드맵대로).
- 실제 uvicorn 서버로 검증한 명령들은 재현 가능하도록 이 문서에 기록해뒀으니, 필요하면
  동일하게 재현해 확인할 수 있다.

### 구현 내역

- **채널별 Redis 스트림 분리**: `app/modules/ingestion/streams.py`(Telemetry, 기존 값 유지)
  옆에 [`app/modules/command/streams.py`](../../../legacy-backend/app/modules/command/streams.py)를
  신설(Command, `aeroops:command:events`/`command-processors`). 둘 다 하드코딩 대신
  `app.core.config.Settings`에서 값을 읽어 `.env`로 오버라이드 가능하게 했다.
- **Redis ACL 자가 등록**:
  [`app/core/redis_acl.py`](../../../legacy-backend/app/core/redis_acl.py)의
  `ensure_channel_acl_users()` — 앱 `lifespan` 시작 시 `ACL SETUSER`로 `telemetry`/`command`
  두 사용자를 만든다. 각각 `~aeroops:telemetry:*`/`~aeroops:command:*` 키 패턴만 허용해
  채널을 물리적으로 분리한다. 별도 `redis.conf`/ACL 파일을 인프라에 배포하지 않아도
  vanilla `redis:7-alpine`(로컬·CI·docker-compose 어디서나 동일)로 동작한다.
- **채널별 Redis 클라이언트**: `app/core/redis.py`에 `get_telemetry_redis()`/
  `get_command_redis()` 추가(기존 `get_redis()`는 관리자/health-check 전용으로 남김).
  `ingestion/router.py`, `telemetry/consumer.py`가 `get_telemetry_redis()`를 쓰도록 변경.
- **`commands`/`command_events`/`event_log`/`deployments` migration**
  (`0002_command_and_deployment_tables.py`): `Command`/`CommandEvent`
  (`app/modules/command/models.py`), `Deployment`/`EventLog`
  (`app/modules/deployment/models.py`). `event_log`/`deployments`는 이번 단계에서 테이블만
  만들고 애플리케이션 코드는 아직 없다(7·8단계에서 실제로 채운다).
- **`POST /commands` 최소 골격**
  ([`app/modules/command/router.py`](../../../legacy-backend/app/modules/command/router.py),
  `repository.py`): `idempotency_key` 유일 제약으로 멱등 생성 — 같은 키+같은 내용 재요청은
  기존 명령을 그대로 반환(200), 같은 키+다른 내용은 409(`IdempotencyConflict`). `Command`
  insert + `command_events`의 `CREATED` 이벤트 기록을 한 트랜잭션으로 처리한 뒤, Command
  Redis Stream에도 best-effort로 발행한다.

### 설계 결정

- **ACL을 인프라 파일이 아니라 앱이 스스로 등록**: GitHub Actions 서비스 컨테이너는 커스텀
  커맨드/볼륨 마운트로 Redis ACL 파일을 주입하기 까다롭다. 앱이 시작할 때 기본(관리자)
  사용자 권한으로 `ACL SETUSER`를 실행하게 하면 로컬 개발·CI·docker-compose 모두 vanilla
  Redis 이미지로 동일하게 동작한다. 관리형 Redis처럼 ACL 명령이 막힌 환경을 위해 실패해도
  앱이 죽지 않고 경고만 남기게 했다(`main.py`의 `lifespan`).
- **`commands` 테이블은 payload 원본이 아니라 `payload_hash`만 보관**: `Command`는 "현재
  상태 스냅샷"이고 전체 내용은 `command_events`의 `CREATED` 이벤트가 보존한다 — telemetry의
  `telemetry_frames`(원본) vs `asset_latest_state`(요약) 구조와 같은 원칙을 그대로 따랐다.
  동일성 판단은 정규화(키 정렬) JSON의 SHA-256으로 한다.
- **Command 생성은 telemetry와 반대로 DB-먼저, 발행은 나중**: telemetry는 "발행 먼저 →
  consumer가 비동기 저장"이지만, command는 idempotency 보장이 핵심이라 "DB 트랜잭션 커밋
  먼저 → 커밋 후 best-effort 발행"으로 순서를 뒤집었다. Redis 발행이 실패해도 명령 생성
  자체(가장 중요한 durable 사실)는 이미 끝나 있다.
- **동시 요청 경쟁 상태**: idempotency_key 중복 여부를 먼저 조회하고 나서 insert하는 사이에
  경쟁이 생길 수 있어(TOCTOU), `IntegrityError`를 잡아 재조회하는 방식으로 이중 방어했다
  (`repository.create_command_idempotent`).
