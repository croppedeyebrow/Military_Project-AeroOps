# 프로젝트 배경·해결 문제·역량 목표

## 1. 프로젝트 설계 배경

AeroOps는 다수의 가상 무인비행체가 시설 점검, 구역 감시, 재난 상황 확인과 같은 모의 임무를 수행하는 환경을 가정한 고신뢰 관제·운용 플랫폼이다.

실제 무인체계 운용에서 관제 시스템이 받는 정보는 항상 완전하거나 최신이라고 볼 수 없다. Telemetry가 지연되거나 일부 Sensor만 갱신될 수 있으며, Command가 전달됐더라도 ACK가 손실되거나 실제 동작 결과가 기대와 다를 수 있다. 여러 운영자가 동시에 개입하면 권한과 통제권 충돌도 발생할 수 있다.

따라서 AeroOps의 핵심은 화면에 드론을 움직이는 것이 아니라 다음 흐름을 검증하는 것이다.

```text
불완전한 운용 데이터 수집
→ 데이터 품질·신선도 판단
→ 기체·임무 상태 해석
→ 권한과 안전 정책 검증
→ 명령 전달·결과 확인
→ 단절 후 재동기화
→ 장애 재생·사후 분석
```

LLM·ML은 이 흐름을 대체하지 않는다. ML은 이상 후보를 탐지하고 LLM은 관련 사건과 절차를 설명하지만, 명령 실행은 규칙 엔진과 권한 검증, 운영자 승인을 통과해야 한다.

## 2. 해결하려는 문제 — 무인체계 운용의 신뢰성과 임무 지속성

### 2.1 불완전한 정보를 바탕으로 임무 상태를 판단하는 문제

관제 화면에서 기체가 정상으로 표시되더라도 해당 정보가 오래되었거나 일부 Sensor만 갱신된 상태일 수 있다. 통신이 끊긴 기체의 마지막 위치를 현재 위치로 해석하면 임무 진행 상황과 운용 위험을 잘못 판단할 수 있다.

AeroOps는 위치, 배터리, 자세, 통신 정보의 신선도를 각각 관리한다. 기체 상태와 데이터 품질 상태를 분리하고, 정상·위험 판단에 필요한 정보가 부족하면 `UNKNOWN` 또는 `판단 불가`로 표시한다.

운영자는 다음 세 종류를 구분해서 확인할 수 있어야 한다.

- 현재 확인된 사실
- 제한된 정보에서 추정한 상태
- 아직 확인하지 못한 정보

### 2.2 통신 제약 속에서 임무를 지속하거나 중단해야 하는 문제

기체와 지상 관제 사이의 통신이 지연되거나 단절되면 중앙 서버의 지시를 계속 기다릴 수 없는 상황이 발생한다. 반대로 통신이 복구됐다는 이유로 단절 중 쌓인 명령을 모두 실행하는 것도 안전하지 않다.

AeroOps에서는 통신 단절 시 적용할 정책을 임무 시작 전에 정의한다.

- 안전 위치에서 대기
- 임무 중단
- 출발지 또는 지정 위치로 복귀
- 현재 임무의 제한적 지속

재접속 시에는 단절 중의 기체 상태와 실행 이력을 먼저 확인한다. 만료된 명령은 폐기하고, 중앙 관제 기록과 기체 기록을 대조해 상태를 복구한다. 통신 장애 대응은 서버 재연결뿐 아니라 기체 측의 사전 정의 Failsafe까지 포함하여 검증한다.

### 2.3 지휘·통제 권한과 명령 충돌을 관리하는 문제

다중 운영자 환경에서는 동일 기체에 상충하는 명령이 요청될 수 있다. 조회 권한, 명령 요청 권한, 승인 권한을 분리해야 하며, 운영자 교대나 관제 인계 과정에서도 현재 통제 주체가 명확해야 한다.

AeroOps는 역할별 권한과 기체별 통제권을 관리한다. 명령 요청자, 승인자, 대상 기체, 적용 임무, 운용 세션과 정책 버전을 기록한다. 상충 명령의 동시 실행은 상태 전이, 낙관적 잠금 또는 통제권 Lease로 차단한다.

통제권 이전 뒤 과거 세션의 명령이 늦게 도착하는 경우에도 실행 시점의 권한, 세션, 만료 시각과 기체 상태를 다시 검증한다.

### 2.4 명령이 실제로 수행되었는지 확인하는 문제

명령 전송 성공, 기체의 명령 수락, 실행 시작, 실행 완료, 목표 상태 도달은 서로 다른 단계다.

복귀 명령에 ACK가 도착했다고 해서 기체가 복귀를 완료했다고 판단할 수 없다. 이후 비행 모드, 경로 변화, Home 도착 조건을 Telemetry로 확인해야 한다.

AeroOps는 Command State와 관측된 Asset State를 연결한다. ACK가 누락되면 즉시 실패 처리하지 않고 `ACK_TIMEOUT` 또는 `UNKNOWN`을 유지한 뒤 실행 이력과 Telemetry를 대조한다. 취소도 접수, 승인, 동작 중지 확인을 구분한다.

### 2.5 개별 기체 상태를 임무 수행 가능성으로 연결하는 문제

배터리 잔량이나 RSSI 하나만으로 임무 지속 여부를 판단할 수 없다. 남은 경로, 복귀 거리, 예상 에너지 소비, Sensor 상태, 탑재체 가용성과 임무 중요도를 함께 고려해야 한다.

AeroOps는 기체의 일반적인 정상 여부와 현재 임무 수행 가능성을 구분한다. 모의 에너지 소비 모델과 경로를 이용하여 잔여 임무와 복귀에 필요한 자원을 비교하고, 판단에 사용한 가정·안전 여유량·입력 신선도를 기록한다.

다중 기체 환경에서는 기체 이탈로 발생한 미수행 구간과 대체 가능한 기체를 표시한다. MVP에서는 자동 재배치가 아니라 운영자의 판단을 지원한다.

### 2.6 제한된 통신 자원을 중요한 정보에 배분하는 문제

다수 기체가 동시에 데이터를 보내면 일반 상태 데이터가 Command, 결과, 긴급 Alert의 전달을 지연시킬 수 있다.

AeroOps는 데이터 유형별 우선순위와 전송 주기를 구분한다.

- Command·Command Result
- 긴급 Alert
- 임무 핵심 상태
- 일반 Telemetry
- 분석·진단 데이터

통신 품질이 낮아지면 일반 Telemetry 전송 빈도를 낮추고, 중요 Event는 보존한다. 논리 채널을 분리한 뒤에도 공유 Network, Redis, Worker, DB에서 병목이 발생할 수 있으므로 혼합 부하에서 명령 지연과 경보 전달 시간을 측정한다.

### 2.7 경보가 많아질수록 중요한 상황을 놓치는 문제

배터리 부족, 통신 저하, 임무 지연이 연속 발생하면 동일 원인에서 여러 경보가 만들어질 수 있다. 운영자는 개별 경보 목록보다 어떤 기체와 임무를 먼저 처리해야 하는지 판단할 수 있어야 한다.

AeroOps는 경보 심각도, 지속시간, 영향받는 임무, 관련 Event를 묶어 Incident로 표현한다. 반복 경보 억제, 확인·조치·해제 이력을 관리한다.

ML은 이상 후보를 탐지하고 LLM은 관련 Event와 절차를 요약한다. LLM 결과는 확인된 사실, 추론, 가설을 구분하고 Evidence Event ID를 포함한다. 근거가 부족하면 원인을 단정하지 않는다.

### 2.8 장애와 운용 판단을 사후에 재구성하는 문제

문제가 발생했을 때 당시 어떤 정보를 확인했고, 어떤 권한으로 어떤 명령을 내렸으며, 어떤 코드·정책·모델이 동작했는지 재구성할 수 있어야 한다.

AeroOps는 원본 Telemetry, Command·승인 이력, 정책 버전, 모델·Prompt·Retriever 버전, 배포 Image Digest와 운영자 조작을 연결한다. 시계 오차와 데이터 누락이 있다면 순서를 확정할 수 있는 범위와 불확실성도 표시한다.

운용 요구사항마다 시험 Scenario와 기대 결과를 정의하여 변경 전후 동작을 비교한다. 구현 기능보다 요구사항, 설계, 시험과 증거의 연결을 프로젝트 핵심 산출물로 본다.

## 3. 프로젝트를 통해 얻고자 하는 실무 능력

### 3.1 CS·소프트웨어 엔지니어링

| 확보하려는 능력 | 프로젝트 작업 | 검증 근거 |
|---|---|---|
| 분산 상태 모델링 | 연결·기체·임무·명령·품질 상태 분리 | 상태 전이표와 불변조건 시험 |
| 비동기·동시성 설계 | 수집·승인·취소·결과 처리 경합 | 동시 요청과 프로세스 종료 시험 |
| 멱등성과 재처리 | 중복·재전송 처리와 명령 효과 중복 방지 | ACK 손실·중복 전송 Scenario |
| 데이터 정합성 | DB 저장·이벤트 발행·원본·Projection 연결 | 장애 지점별 데이터 대조 |
| 시간·순서 처리 | Event/Received Time, Sequence, Session | 역순·시계 오차·재시작 시험 |
| Interface 설계 | 단위·좌표계·오류·호환성 명세 | 데이터 계약과 ICD |
| 성능·자원 제어 | Queue·Backpressure·QoS | 처리량·지연·대기열 측정 |
| 운영·복구 | 관측성·배포·백업·복구 | 장애 분석과 복원 기록 |
| 요구사항 기반 검증 | 운용 요구와 시험 연결 | Traceability Matrix |

최종 목표는 “요청이 실패했다”는 현상을 데이터, Process, Network와 상태 전이 관점에서 분해하고 복구 방법과 한계를 설명하는 능력이다.

### 3.2 AI·ML

| 확보하려는 능력 | 프로젝트 작업 | 검증 근거 |
|---|---|---|
| 문제 정의 | 기체 이상·Sensor 오류·통신 누락 분리 | 과제 정의와 Label 기준 |
| 데이터·Feature 설계 | 배터리·운동·자세·통신 특징 생성 | 품질·Feature 명세 |
| 기준 모델 | 임계값·통계 규칙·ML 비교 | 동일 평가셋 결과 |
| 누수 없는 평가 | 시간·비행·기체·Run 단위 분리 | 분할·재현 기록 |
| 운용 지표 | 오경보·미탐·탐지 지연·경보 빈도 | Scenario별 성능 보고서 |
| 불확실성 | 품질 저하·미경험 조건에서 보류·Fallback | OOD·품질 저하 시험 |
| 자체 LLM·RAG | 문서·Event 검색과 근거 설명 | 검색·근거·Hallucination 평가 |
| 추론 운영 | 메모리·지연·모델 장애 관리 | 자원·Fallback 결과 |
| MLOps | 데이터·전처리·모델·정책 Lineage | 재현·Rollback 기록 |

시뮬레이터는 실제 Fault 주입 원인을 알고 있지만, 모델 입력에는 운용 당시 관측 가능한 정보만 제공한다. 미래 정보나 정답 Label이 Feature에 섞이는 Leakage를 방지한다.

LLM은 설명과 보고서 초안만 생성한다. 실행 권한과 분리하며 근거 부족 상황에서 원인을 단정하지 않는지 평가한다.

### 3.3 도메인

| 임무 가용성 | 배터리·경로·Sensor·통신을 임무 가능성과 연결 | 임무 제약·판단 규칙 |
| 장애 대응 정책 | 링크 손실·Sensor 실패의 조건·우선순위 | Failsafe와 복합 장애 시험 |
| 통제권·인계 | 역할·승인·운영 Session 유효성 정의 | 권한표와 인계 Scenario |

| 체계 통합·시험 | 운용 요구를 Interface·시험 조건으로 변환 | ICD와 요구사항 추적표 |
| 운용·정비 Feedback | 경보·실제 모의 장애·조치 결과 대조 | 사후 분석과 개선 이력 |

AeroOps에서 경험하려는 핵심은 운용 요구를 기술 요구사항으로 변환하고, 구현 결과가 그 요구를 충족하는지 증거로 검증하는 과정이다. 가상 환경에서 확인한 결과와 실제 장비 연동 시 추가 검증해야 할 항목을 구분하여 기록한다.

## 5. 프로젝트 경계와 한계

- 실제 Flight Controller와 비행 안전 인증을 대체하지 않는다.
- 정밀 6-DOF 비행역학이나 RF Propagation 인증 모델을 구현하지 않는다.
- 실제 전파 방해, 침투, 무장·표적화·공격 기능을 다루지 않는다.
- 가상 Scenario의 결과를 실제 기체 안전성 근거로 직접 일반화하지 않는다.
